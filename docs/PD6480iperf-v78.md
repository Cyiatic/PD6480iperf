# v78: adaptive room cache and reserved portal workspace

Known War opening freeze. Not a working full-game, Analogue-verified or
benchmarked release.

## Subsequent War failure and cause

The completed 21-mission Perfect Agent matrix passes 20 initial mission starts,
but War freezes in its opening at level frame 165. Cause `0x0000000c`, saved PC
`0x8001b7e4` (`modelInitRwData+296`), BadVAddr `0x3f800000`: initializing a debris
model attempts to write its toggle flag through a corrupted rwdata pointer.
There is no allocator-failure marker and about 1.10 MB stage space remains.
The v77 matching-state control reproduces the War freeze, so this is not new
to the adaptive-cache change.

The pad generator's header advertises every JSON cover record, while
`make_cover` emits only records whose `special` field is zero. Four generated
files have counts beyond their actual cover data: mp1 178/177, pam 582/263,
sho 425/200, and stat 425/200 (advertised/emitted). War uses stat.
`setupPrepareCover` therefore operates beyond the loaded file and its look-vector
normalization overwrites neighboring model bindings with zeroes and float 1.0.
The compressed streams are valid: a structural count/bounds audit is required
in addition to the compression check. The follow-up fix advertises only emitted
records, preserving the performance generator's existing special-record filter.

Do not infer that the 20 initial passes establish safety in those levels: sho
and pam are shared by missions which passed their short initial checks.

## Why v77 was replaced

Perfect Agent Infiltration and Rescue exhausted their stage pools before the
first level frame while their separately reserved 512,000-byte room caches
were still empty. Reducing that reservation to 256 KiB alone was insufficient:
both then failed the later 120,080-byte persistent portal-distance allocation.

Source review also found that the portal-distance calculation used the next
stage-allocation address as temporary scratch without reserving its size. Under
memory pressure this can overlap allocations from the other end of that pool.
This is a source-level overlap hazard, not proof that every historical Analogue
crash was caused by it.

## Changes

- Reserve an initial 128 KiB room cache. After required level setup, append a
  separately owned bank toward the original stage target (minimum target
  256 KiB), only using stage space above a 128 KiB reserve. No live allocation
  is moved and holes between the banks are never treated as free memory.
- Use the idle full-size depth allocation for the temporary portal-distance
  workspace during level loading, with a capacity check. The persistent
  triangle of portal distances remains in the stage pool. The previous frame's
  graphics work is drained before stage replacement; normal rendering clears
  the depth buffer before using it.
- Keep the existing fixed 640x480 colour/depth storage, HAF1 interlaced gameplay
  output, L graph and framebuffer readout. The legacy Hi-Res option changes its
  stored flag only: both modes already render at full resolution.

The v77 bounded retention policy remains: visited rooms can remain cached while
the largest free block is at least 64 KiB. Whole-level preloading remains off.
This is not a claim to preserve that optimization or a measured speed increase.

## Emulator evidence

ParaLLEl N64 1.0 2f3bf60, cached-interpreter CPU, cxd4 RSP, Angrylion RDP,
8 MiB RDRAM. Emulator frame counts are not console performance benchmarks.
Save-dependent tests use the documented in-memory ED/16-Kbit EEPROM header
adapter. The disk ROM uploaded to hardware is not changed by that adapter.

Every restored state was generated by this exact build and the same adapter.
Restoring a state from another ROM would restore old resident game code and
invalidate the test; those states must never be mixed.

The test tooling now compares six key resident functions against the matching
ELF before accepting results. The v78 baseline matches; an actual v77 briefing
snapshot is rejected at `mainLoop`. This is a targeted code-identity check, not
a complete-ROM equivalence proof. Matrix results produced before adding the
check are rechecked using their completed RDRAM snapshots.

### Real menu inputs and Hi-Res

A fresh 5,100-tick boot selected Dark through the menus, entered Carrington
Institute, enabled the L graph and navigated to a mission briefing. Normal
controller inputs then opened Video Options and enabled Hi-Res. From that
matching state:

- A switched Hi-Res off; 900 further ticks produced 900 frames, Hi-Res=0,
  640x480 active dimensions and no allocation-failure marker.
- A separate continuation retained Hi-Res=1, closed the menu with Start and
  applied stick movement. It produced 1,499 frames in 1,500 ticks, changed the
  camera view and advanced the level-frame counter from 603 to 1,308 without
  an allocation failure. Active dimensions remained 640x480.

### Mission-load coverage

The matrix runner changes only the menu-selection word (stage, index, Perfect
Agent, solo) in a matching briefing state. Normal A input invokes Accept Mission;
Start skips the opening after loading, followed by brief stick movement. This
is explicitly instrumented menu selection, not an unmodified UI walkthrough.

The initial six-stage batch passed in Infiltration, Rescue, Escape, Maian SOS,
Defection and Crash Site. A separate Skedar Ruins run also passed. Each reached
normal, non-cutscene gameplay with advancing level frames, 640x480 active
buffers and no recorded allocation failure.

Area 51 remains memory-constrained: Infiltration and Rescue have only about
92 KB of uncommitted stage space and a 128 KiB room cache at these snapshots.
An initial load pass does not establish that every later room, texture load or
long session fits. The additional 2,700-tick batch passes Investigation,
Extraction, Villa, Chicago, G5 Building, Air Base, Air Force One, Pelagic II,
Deep Sea, Defense, Attack Ship, Mr. Blonde's Revenge and Duel. War fails as
described above. Air Force One has only 120,576 free stage bytes at its snapshot.

## Automated checks

- Both gameplay mode entries are 640x480 with 640-pixel stride.
- Colour allocation: 1,228,864 bytes. Depth allocation: 614,464 bytes.
- All 1,403 compressed assets validate; 608 raw entries remain unaudited by that
  compressed-stream check, and two entries are empty aliases.
- All 12 existing allocation/asset/save regression tests pass.
- Three additional resident-code tests check matching bytes, altered code and
  truncated RAM (15 Python regression tests in total).
- The actual `mema.c` passes host tests for appended banks, live pointers,
  allocation/free/defragmentation, gap exclusion, cross-bank growth rejection,
  within-bank growth/shrink, invalid-bank rejection and reset. A deterministic
  10,000-operation fragmented workload checks live-block ownership, absence of
  overlaps and conservation of free-plus-allocated bytes after every operation.
- The actual `bgTickRooms` passes the retention-threshold, eviction-cap,
  visible-room protection and young/unloaded-room checks.
- Xdelta decoding against the stock V1.1 base reproduces the exact tested ROM.
